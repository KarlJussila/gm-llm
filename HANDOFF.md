- **Task now: recalibration 1 — `turn-reminder` as an executable algorithm (effort: high).**
  Grant `dm-runner` the `todowrite` tool (it is the only agent in the corpus without it) and
  rebuild the per-turn brief as a list the runner executes, with **triggers** for re-loading a
  skill and re-reading canon. This runs before the rows that author rule prose because it
  decides whether those rules can live in a skill at all.
- **Read first:** `design/runner-authority.md` § Delivery — it is measured, not argued, and it
  is the reason this row exists. Then § The model (six rules, settled) and the audit table.
- **The trap:** the reminder is the scarcest real estate in the system, and the instinct is to
  add the rules to it. The bet of this row is the opposite — make loading reliable and the
  reminder gets *shorter*, becoming a dispatch list rather than a rulebook. Re-loading a
  hundred-line skill every turn is its own cost, so the list wants cheap steps unconditional and
  expensive ones gated on a condition.
- **Measurable without the grader.** Skill loads, mid-session reads and greps are deterministic
  rows in opencode's session DB (`part` rows of type `tool`, joined to `session.agent`). One
  run tells you whether the algorithm took. No baseline is banked and the pilot's is superseded,
  so this is the only signal available — use it.
- **Watch for:** the runner is the one agent the player can see, and a todo list is process.
  `dm-runner` already forbids narrating its own process and the gate has caught a meta-break. If
  leakage rises, `design/open-questions.md` carries the structural answer (submit the turn
  through a tool) as a conditional item — raise it, don't build it unasked.
- **Needs Karl:** the live-model shakedowns; model configuration ownership; whether
  `dev/test_*.py` should become pytest.
- **Also open (unblocked):** docs 1 (low) — generate `findings.md` § Contents; the lint has
  caught a missing row in consecutive rounds now. frontends 5 (low), benchmark 3 (low,
